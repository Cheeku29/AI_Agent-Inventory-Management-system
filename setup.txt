INDUSTRY-LEVEL PROJECT SETUP + ARCHITECTURE
============================================================

PROJECT NAME
AI Inventory Decision Engine

============================================================
1. PRODUCT OBJECTIVE
============================================================

Build an industry-level AI Inventory Decision Engine for
quick-commerce dark stores.

The system acts as an intelligence and decision layer on top
of existing inventory/WMS/ERP/procurement systems.

The system should transform:

"What is happening?"

into:

"What is likely to happen?"
"Why is it happening?"
"What should we do?"
"Which action is most urgent?"

The application must eventually support:

- User authentication
- Google login
- Dataset/workspace creation
- CSV upload
- Automatic dataset profiling
- Automatic schema understanding
- Schema mapping
- Large-scale data processing
- Demand forecasting
- Stockout prediction
- Overstock detection
- Inventory anomaly detection
- Phantom inventory detection
- Expiry risk detection
- Replenishment optimization
- Priority scoring
- AI explanations
- Human approval of recommendations
- AI Inventory Copilot
- Audit history

3. AGENT ARCHITECTURE
============================================================

There are FIVE agentic components.

IMPORTANT:

Do NOT implement five independent LLM chatbots.

Use one primary AI Copilot/Supervisor workflow with
specialized capabilities/tools.

The architecture should be:

USER
 ↓
AI COPILOT / LLM
 ↓
SUPERVISOR AGENT
 ↓
 ┌───────────────────────┬──────────────────────┐
 ↓                       ↓                      ↓
DATA AGENT           RISK AGENT          FORECAST &
                                          OPTIMIZATION
                                          AGENT
 ↓                       ↓                      ↓
 └───────────────────────┴──────────────────────┘
                         ↓
                  FINAL EXPLANATION
                         ↓
                        USER


============================================================
4. AI COPILOT
============================================================

Technology:

Gemini

Framework:

LangGraph

Purpose:

The AI Copilot is the natural-language interface.

Examples:

"What should I order today?"

"Which products are at risk of stockout?"

"Why is SKU 123 high priority?"

"Which products are overstocked?"

"Show me unusual inventory movements."

"Why should I order 50 units?"

The Copilot should NOT invent numerical values.

It must call tools and use actual results from the system.

============================================================
5. SUPERVISOR AGENT
============================================================

The Supervisor is the central orchestration layer.

Responsibilities:

- Understand user intent
- Determine which specialist capability is required
- Select appropriate tools
- Coordinate multi-step analysis
- Pass context between specialist agents
- Combine results
- Decide when enough information has been collected
- Ask the user for clarification when required
- Return a final explainable answer

Example:

User:

"What should I order today?"

Supervisor:

1. Call inventory tool
2. Call demand forecast tool
3. Call risk tool
4. Call replenishment tool
5. Rank recommendations
6. Return explanation

The Supervisor should be implemented using LangGraph.

============================================================
6. DATA INTELLIGENCE AGENT
============================================================

Purpose:

Understand newly uploaded datasets.

Responsibilities:

- Inspect uploaded files
- Identify file types
- Understand columns
- Detect data types
- Detect date columns
- Detect identifiers
- Detect numeric fields
- Detect categorical fields
- Detect missing data
- Suggest dataset roles
- Map arbitrary column names to canonical fields
- Validate schema
- Report data quality problems

Example:

Uploaded:

inventory_2026.csv
sales_history.csv
vendors.csv

The Data Agent may determine:

inventory_2026.csv
→ Inventory

sales_history.csv
→ Sales

vendors.csv
→ Supplier

It must support arbitrary filenames and column names.

============================================================
7. INVENTORY RISK AGENT
============================================================

Purpose:

Identify inventory risks.

Responsibilities:

- Stockout risk
- Overstock
- Expiry risk
- Inventory anomalies
- Phantom inventory
- Unusual stock movements
- Demand/supply mismatch
- Slow-moving inventory

The Risk Agent should consume outputs from deterministic
ML models and analytics.

Do NOT allow the LLM to invent risk scores.

Risk calculations must come from actual analytical
services.

============================================================
8. FORECAST & OPTIMIZATION AGENT
============================================================

Purpose:

Determine what action should be taken.

Responsibilities:

- Demand forecasting
- Expected demand
- Safety stock
- Reorder point
- Replenishment quantity
- Supplier lead-time considerations
- Incoming stock
- MOQ
- Pack size
- Priority scoring

Output should include:

SKU
Product
Current stock
Forecast demand
Risk
Recommended quantity
Priority
Reason
Confidence

The actual numerical calculations must be performed by
ML/optimization services.

The LLM only interprets and explains those results.

============================================================
9. MACHINE LEARNING LAYER
============================================================

Use:

LightGBM
scikit-learn
NumPy
Pandas

ML capabilities:

1. Demand forecasting
2. Stockout prediction
3. Inventory anomaly detection
4. Overstock detection
5. Expiry risk prediction

Keep model training separate from the production API.

Training code:

ml/training/

Inference:

backend/app/ml/

Model artifacts:

ml/models/

The system must eventually support training using large
datasets on Google Colab GPU.

The laptop must not be required to have a GPU.

============================================================
10. LARGE DATA PROCESSING
============================================================

The dataset may contain millions of rows.

This is a critical architecture requirement.

DO NOT:

- Load entire CSVs into RAM
- Build giant Python dictionaries
- Build millions of Python objects
- Store all candidate pairs in Python lists
- Perform unnecessary pandas operations on entire datasets

Use:

DuckDB
PyArrow
Parquet
SQL
Streaming
Chunk processing
Disk-backed intermediate tables

Pipeline:

CSV
 ↓
File validation
 ↓
DuckDB/PyArrow
 ↓
Parquet
 ↓
SQL transformations
 ↓
Feature generation
 ↓
ML inference
 ↓
Optimization
 ↓
Recommendations

Pandas may be used for small samples and ML operations where
appropriate.

============================================================
22. AGENT RULE
============================================================

The agents must NOT directly manipulate raw data blindly.

Agents should call controlled backend tools.

Create tools such as:

get_inventory()
get_sales()
get_forecast()
get_stockout_risk()
get_anomalies()
get_overstock_risk()
get_expiry_risk()
get_replenishment_recommendations()
get_action_queue()
get_product_details()

Numerical outputs must originate from backend services,
database queries, ML models, or optimization logic.

The LLM explains the results.

The LLM must not invent:

- Stock quantities
- Forecast values
- Order quantities
- Risk scores
- Prices
- Dates
